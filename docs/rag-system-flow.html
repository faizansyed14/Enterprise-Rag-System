1–9. Ingestion: source to searchable index

The pipeline is asynchronous and idempotent. Each stage can be retried without intentionally duplicating the document.

1

Source event or upload arrives

entry

A scheduled connector sync, manual upload, or source refresh creates a remote item/job. The item carries a source identity, path/name, size, timestamps, ETag/change token, content type, and ACL principals.

  • SharePoint document libraries and OneDrive for Business use Microsoft Graph.
  • Filesystem/SMB and legacy connectors are also available.
  • Uploads enter through the API and object-storage path.

connectors/base.py · connectors/sharepoint.py · uploads.py

2

Acquire bytes and establish identity

idempotency

The connector downloads the raw file, computes a content hash, normalizes the source identity, and compares it with the last known item. Unchanged items can skip expensive parsing and embedding work; changed items create a new processing path.

  • SharePoint/OneDrive content is a binary driveItem stream.
  • ACL changes are tracked separately from content changes.
  • Large files and retries are handled by job/connector limits.

pipeline.py · graph_client.py · schema.py

3

Store the original and source metadata

durable source

The original bytes are retained in object storage. PostgreSQL stores the source, document identity, version/revision, file metadata, ACL principals, job state, hashes, and processing lineage. Qdrant is not the source of truth; it is a derived search index.

storage/objects.py · db/schema.py

4

Classify the file and choose a parser route

dispatch

Content type, file extension, page characteristics, and configured parser decide which extraction branch is used. The result is page/section-oriented text and structure, not yet vector data.

Parser routes are shown in detail below

Normal digital PDF, scanned PDF, image-only page, Office files, and optional cloud/layout parsers all converge into a common page/blocks representation.

ingestion/formats.py · parsers/pdf.py · parsers/cloud.py

5

Normalize text, pages, tables, and metadata

canonical form

Extracted blocks are cleaned and labeled with page numbers, headings, table context, coordinates where available, language, and parser details. Metadata extraction identifies project, discipline, document number, title, dates, revision, references, and confidence.

  • Identifiers and revision data help exact retrieval and “current revision” selection.
  • ACL principals stay attached to the document/version so they reach every chunk.
  • Low-quality or empty extraction can trigger OCR/fallback handling.

metadata/extract.py · metadata/title_block.py · metadata/identifiers.py

6

Chunk by structure and page boundary

retrieval units

The chunker keeps document headers, headings, page numbers, table labels, and nearby context. Chunks are token-limited and retain document/version/page/source references. Near-duplicate fingerprints support family detection and later ranking demotion.

ingestion/chunker.py · text/minhash.py

7

Create searchable representations

models

Each chunk gets multiple retrieval representations:

  • Dense embedding from the configured embedder/model server, with the correct query/passage behavior.
  • Sparse BM25-style tokens/weights from the configured analyzer.
  • Exact identifier signals for document numbers, revisions, RFIs, and similar codes.

embedders/local.py · model_server/engine.py · text/bm25.py

8

Build a versioned Qdrant collection

derived index

Vectors and payloads are written to a build-specific collection. Payloads include document/version/page/chunk identity, project/type/discipline, revision/current/published state, ACL principals, source, and text needed for evidence display. Payload indexes support filtered search.

vectorstore/qdrant.py · ingestion/index_builds.py

9

Validate, publish, and expose the live alias

publish boundary

Build counts and consistency checks run before activation. The new collection is promoted through an alias/active-build record so readers see a complete index rather than a partially built one. Old builds can remain available for rollback or comparison.

Important separation: PostgreSQL records what the system believes is current and allowed; Qdrant accelerates retrieval. The final answer path rechecks critical access/current-version conditions before evidence is used.

index_builds.py · pipeline.py

Parser routes: what happens to each file type?

All routes eventually return page/section content for metadata extraction and chunking, but their evidence quality is different.

Normal digital PDF

Text exists in the PDF content stream, so OCR is not required.

PDFium text / character extractionReads text, coordinates, rotation, Unicode, reading geometry, and page boundaries.
→
Structure and layoutHeadings, columns, title blocks, table candidates, captions, and page blocks are assembled.

pdf.py · layout_runner.py · layout/main.py

Digital PDF with tables

Text extraction and table detection run together when table structure is available.

Table candidateRuled lines, cell geometry, captions, and neighboring text are identified.
→
Table blockRows/labels are represented as chunkable text with page provenance.

table_flow.py · table_quality.py

Scanned PDF

There is little or no selectable text, so pages are rendered or read as images.

Page imageRender the page or use the supplied image region.
→
OCRRapidOCR, Azure/Mistral OCR, or OCR=vision/default using the configured VISION model returns text and sometimes regions/coordinates. VisionOCR sends the image to the OpenAI-compatible endpoint, including OpenRouter, and falls back to local RapidOCR when it fails or returns empty text.

ocr/rapidocr.py · ocr/cloud.py · ocr/vision.py

Image files / image-only pages

Images follow the OCR role directly. OpenRouter is reached through the VISION role when OCR=vision/default is selected.

Image safety and sizingDecode, resize, limit pixels, and select OCR/vision route.
→
Text + regionsOCR output is normalized into the same page representation as PDF text.

ocr/vision.py · ingestion/ocr_cache.py

OpenRouter OCR, exactly

The code uses two roles: VISION=openrouter/<vendor>/<model> selects the vision chat model; OCR=vision/default makes the hub construct VisionOCR around it.

Its prompt requests exact Markdown transcription, headings, tables, figures, and handwriting. Image shrinking, privacy preflight, page budgets, OCR cache, and local fallback surround the model call.

plugins/hub.py · providers/ocr/vision.py · providers/llm/openai_compat.py

Word / Excel / PowerPoint

Office parsers extract text, paragraphs, sheets, rows, cells, and presentation content. Office previews can be used where a visual representation is needed.

ingestion/formats.py · formats_extra.py · office_preview.py

Optional cloud/layout parser

Azure Layout, LlamaParse, or Mistral adapters may be selected for difficult files. They are not required for the local path and their output is adapted into the common internal representation.

parsers/cloud.py · layout/adapter.py

Common convergence point: regardless of source type, the parser should produce page-aware text/blocks, table context, coordinates where available, extraction metadata, and quality signals. The chunker then creates the units that are embedded and searched.

What is stored where?

Three stores have different responsibilities; the vector database is not the archive.

01Object storage

Original bytes

  • PDF, DOCX, XLSX, images, and other source files.
  • Content-addressed storage and download/replay source.
  • Used when a page preview or reprocessing is needed.

02PostgreSQL

System of record

  • Sources, documents, versions, revisions, pages, chunks, jobs, ACLs.
  • Current/published state and index-build metadata.
  • Evaluation runs, audit events, and operational state.

03Qdrant

Derived search index

  • Dense vectors and sparse vectors.
  • Payload filters for ACL, project, revision, source, type, and page.
  • Chunk text and provenance needed to return evidence.
Rebuild rule: if parser, OCR, chunker, tokenizer, embedder, or analyzer behavior changes, the safe pattern is to build a new version, compare it, and activate it atomically. The original bytes must remain available for that rebuild.

Question path: request to evidence

This is the live path after a user submits a question.

1. API + identity

Chat endpoint authenticates the user and resolves principals/groups.

2. Guardrail

Blocks unsafe questions and neutralizes unsafe evidence handling.

3. Query router

Rules classify language, identifiers, project/revision hints, follow-up context, and hard/research cases.

4. Filter plan

ACL, published/current version, project, type, date, source, and local-only constraints are prepared.

5. Retriever

Runs parallel retrieval legs and returns ranked documents/passages.

Dense leg

Embed the query and search the dense Qdrant vector field for semantic similarity.

Sparse leg

BM25/analyzer search preserves exact terms, codes, names, and construction vocabulary.

Exact / translated legs

Identifier matching and translated sparse search help document numbers and cross-language queries.

Post-processing

Fuse, deduplicate, demote near-duplicate families, optionally rerank, recheck access/current state, cap passages, and expand same-page context.

api/routers/chat.py · security/principals.py · retrieval/query_router.py · retrieval/retriever.py

Evidence boundary: the answer model should only see passages returned for the user’s principals and filters. Retrieved source text is untrusted content; it is evidence, not instructions.

Answer path: evidence to final response

The answer is streamed, then checked before the request completes.

A

No evidence branch

abstain

If retrieval returns no passages, the agent emits a localized “not found” response and stops before generation.

B

Choose answer model

LLM_ANSWER

Normal questions use LLM_ANSWER; hard/multi-part/research questions can use LLM_ANSWER_HARD. If a cloud model is used, local-only documents are excluded by the plan.

answering/agent.py · config/roles.py

C

Build grounded prompt and stream

generation

The user question, conversation history, and sanitized evidence passages are placed into the answer prompt. The model streams answer deltas; an optional read-only research/tool loop can request more searches for hard questions.

answering/prompts.py · answering/tools.py · providers/llm/extractive.py

D

Strip markers and verify citations

post-check

Answer citations are parsed and matched back to the supplied passages. Each citation carries source/document/page information for the UI and audit trail.

answering/citations.py

E

Run groundedness check and set status

post-check

The configured groundedness provider checks the answer against evidence. The result becomes ok, unverified, not_found, refused, or error, with citations and timing/usage attached.

answering/grounding.py · providers/groundedness/judges.py

F

Return to the client

response

The API/SSE stream delivers status, answer deltas, citation events, and a final completion payload. Traces and metrics record plan, retrieval, generation, verification, latency, model, and counts without storing unnecessary question/answer text in telemetry.

api/sse.py · monitoring/tracing.py · answering/agent.py

Current implementation notes

These are useful when reading the flow against the current configuration.

What is mandatory?

Connector/ upload, original storage, PostgreSQL metadata, parser output, chunking, dense/sparse representations, Qdrant build, filtered retrieval, evidence prompt, citation/groundedness post-check, and API response.

What is optional?

Cloud parsers, cloud OCR, vision OCR, LLM query routing, cross-encoder reranking, research tools, and stronger groundedness judges. Their availability depends on settings and provider/model registration.

Important separation

Parsing creates evidence; chunking creates retrieval units; embeddings make semantic search possible; Qdrant ranks candidates; PostgreSQL/ACL logic determines what may be used; the answer model writes prose.

Current role configuration

OpenRouter OCR is activated through OCR=vision/default, not OCR=openrouter/.... The current local .env still has OCR=local/rapidocr and VISION=none; changing the role affects new extraction jobs, and existing files need rag reparse.

config/settings.py · config/roles.py · cli.py (reparse)

Recommended reading order

Start with pipeline.py, then formats.py, chunker.py, retriever.py, and finally agent.py.

Source-audited against executable connector, ingestion, parser/OCR, model hub, storage, indexing, retrieval, answering, and evaluation paths. Optional branches are labeled as such; links point to implementation files so the flow can be checked against source.
